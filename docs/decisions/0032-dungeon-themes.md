# ADR 0032: Dungeon themes

Status: Accepted (2026-10-21). Home: `internal/layer2/gamedata` (the field, the filling and the check), `cmd/internal/themes` (the embedded pictures), `cmd/gozen` (`gozen theme`).

## Users and problem

An author who wants a first-person dungeon has to paint, or find, a wall, a floor, a ceiling and a door that match each other and tile without a seam, and write each path in `dungeon:`. Go Zen ships two such sets (brick and pipe) inside its own assets; another game cannot name them.

## Decision

### YAML: `theme` in `dungeon` and in each of `looks`

```yaml
dungeon:
  theme: cave            # walls, floor, ceiling, door and colors from the cave theme
  looks:
    - when: floor >= 3
      theme: ice         # the deeper floors in another theme
```

A theme is a folder `assets/dungeon/themes/<name>/` of the game. It holds `wall.jpg`, `floor.jpg`, `ceiling.jpg`, `door.jpg` (1024x1024, the first three tile without a seam) and `theme.yaml` with the `floor` and `ceiling` colors (the far fog and the map). `theme: cave` fills `wall`, `door`, `floor_texture`, `ceiling_texture`, `floor` and `ceiling` from it when the game loads. Anything written beside it wins: those six keys keep working as today and take priority over the theme, in the dungeon and in each look. A look with a theme replaces the dungeon's theme for what it does not write itself. A theme has no stairs and does not change tiles; a tile names its own picture as before.

A theme name is lowercase letters, digits, `-` and `_`, starting with a letter. The folder is plain game assets: an author may edit it, or make one of their own by that name without using the command.

### Where the pictures come from: the `gozen` command

The themes (`cave`, `ice`, `ruins`, `castle`, `crystal`, `temple`, `sewer`, `forest`, `tomb`) are embedded (`go:embed`) in `cmd/internal/themes`, a package only the `gozen` command imports. The runtime (`play`, `gfx`, `schema` and the root package) never does, so a game binary and `go get github.com/nao1215/gozen` stay as small as before, and a game that uses no theme carries no picture. `go-arch-lint` forbids `play` to depend on the commands, and a test lists the dependencies of the runtime packages to say it again.

- `gozen theme list` prints the names with a line on each.
- `gozen theme add <name> <game-dir>` copies the five files, with the license of the pictures as `LICENSE.txt`, to `assets/dungeon/themes/<name>/`. It needs no network. A file the game already has is kept (the command says `kept`); `--force` replaces it. An unknown name exits 2 with GZN2402; a directory without `game.yaml` exits 1 with GZN1110.

The pictures were generated by the author, made to tile, and are CC BY 4.0 like the rest of the generated art of the repository (ASSETS.md).

### Checks

`gozen check` reports GZN1111 when a dungeon or a look names a theme and the game lacks the folder or one of its five files, with the line `run gozen theme add <name> <game-dir>`; the pictures filled from the theme are not reported a second time as missing assets. A `theme.yaml` that cannot be read (a color that is not `#rrggbb`, an unknown key) is a GZN1104, and a name that is not a theme name a GZN1107.

## Alternatives

1. Embed the themes where the runtime can serve them (`play` or the module root). Every game binary and every `go get` would carry all the themes, used or not. Rejected: a game that uses no theme must not get heavier.
2. A separate Go module (`themes/go.mod`) that a game imports. The binary would carry only what the author imports, but `play` would need a way to receive the module's files (a new option of `play.Main` or a registry), which is new public API, and the module needs tags of its own, the cost that [ADR 0009](0009-single-module.md) removed. Rejected.
3. A zip of the themes attached to each release, or a command that downloads them. It makes the author find and unpack a file by hand, or makes the CLI depend on the network and on a hosting place that can move or fail, and an offline build or a CI run cannot add a theme. Rejected: the pictures in the binary work offline and match the version of the command. Revisit this when the bundled assets grow past a few tens of megabytes: then `gozen theme add` can fetch a release asset and check it against the release checksums and provenance, the way `gozen art fetch` pins the detection models it downloads.
4. Resolve the theme while drawing, reading the folder at run time. The loader would then not know the final pictures, `Styled` and the checks would each repeat the rules. Rejected: filling the fields once at load keeps the drawing code and the looks as they are.

## Consequences

- `api/public.txt` does not grow. `api/schema.txt` gains `DungeonLook.Theme` and `Dungeon.Theme`. The schema version does not change: an older file has no `theme`.
- The `gozen` binary grows by about 3.5 MB (twenty JPEG pictures at 1024x1024).
- One diagnostic is added, GZN1111 ThemeMissing, and one command group, `theme`.
- A new theme is a folder of five files in `cmd/internal/themes/assets/<name>/` and a line in the summaries of the package; its tests check the size and format of every picture.
