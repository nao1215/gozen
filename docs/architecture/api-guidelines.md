# API の命名と形

この文書は v0 の実装に適用する規約です。T2 の実装済み契約と利用例は [中核 API](core-api.md) を参照してください。

## 公開の判断

既定は `internal/` です。公開する型・関数・メソッド・フィールドごとに、利用者とその目的を説明できることを条件にします。ゲーム側から使わない補助関数、テストだけが使う関数、単なる中継 interface は公開しません。実際の利用例、godoc の契約、`api/public.txt` の差分を同時にレビューします。

## 入口の統一

| 種類 | 形と意味 |
| --- | --- |
| FS からの読み込み | `Load(fsys fs.FS, path string) (T, error)`。`path` は FS 内の相対パス。ディレクトリを対象にするときは `.` を受け付ける |
| メモリからの解析 | `Parse` を使い、ファイル探索や OS の読み書きをしない |
| 検証 | `Validate` を使い、入力を変更しない。通常の不正入力は error で返す |
| インスタンス作成 | `New(..., cfg Config)`。失敗し得る場合は `(T, error)`。同じ種類の入口で戻り値の形を揃える |
| 設定 | 小さな `Config` 構造体を採用する。関数型 Option や `With...` の系列を併設しない |
| 長時間・中断可能な実行 | `Run(ctx context.Context, ...) error` のように context を最初に置く |
| 同期的な純粋計算・FS 読み込み | context を足さない。ネットワークやバックグラウンド処理を読み込みに隠さない |

`Config` のゼロ値の意味、既定値、許される値を godoc に書きます。設定は必要な利用者のための項目に限り、エンジンの内部状態や調整用のフィールドを大量に露出しません。必須の協力相手と設定値を区別し、不正な設定を黙って補正しません。

## エラーと副作用

ライブラリは `os.Exit`、`log.Fatal`、入力不正での panic を使いません。エラーは最後の戻り値とし、原因を保つ必要がある場合は `%w` で包みます。エラー時の戻り値は原則として利用不可です。複数の診断が必要なら専用の検証結果として契約を設計し、成功と見分けのつかない半端な状態を返しません。

CLI のプロセス終了は `main` の責務です。stdout は結果、stderr は診断に用います。出力・保存・Close の失敗を握り潰しません。API に渡した reader/writer/FS の所有権、閉じる責任、入力の変更可否を説明します。暗黙の作業ディレクトリ変更やプロセス環境の書換えを避けます。

## CLI

CLI は `gozen` の 1 本で、`go install github.com/nao1215/gozen/cmd/gozen@latest` で導入できる構成にします（[ADR 0016](../decisions/0016-single-cli.md)）。汎用のサブコマンドは `cmd/gozen`、制作支援の `prompt`・`mosaic` の実装は各専用 internal の `command` パッケージに収めます。推論アダプタは cgo ビルドと推論なしビルドを分け、cgo なしの `gozen` は推論が必要な時に不足を診断して非ゼロで終了します。[制作支援 CLI](../development/production-tools.md) に要件を記載します。公開版の導入確認はリリース後に行います。[CLI の使い方](../development/cli.md) に実行例と前提を記載します。

`gozen` とその各サブコマンドの `--help` は `Requirements` 欄を持ち、そのサブコマンドに必要な外部の物だけを列挙します。cgo の C コンパイラ、ONNX Runtime の共有ライブラリ、利用者指定のモデル、画面検査の Xvfb などは、実装で必要と確認したものだけを示します。外部前提がなければその旨を明示します。help 自体は推論や画面の初期化なしで成功させます。

同じ欄に README の対応節（`README.md#gozen`、公開 URL は `https://github.com/nao1215/gozen#gozen`）への案内を載せます。インストール先でも辿れる公開 URL を示し、README の節から OS 別の準備手順へ案内します。cgo が必要なサブコマンド（`mosaic` の推論）と不要なサブコマンドを区別して記載します。

起動に必要な外部の物が足りない場合は、何がないか・どう準備するかを stderr に短く表示し、同じ README 節へ案内して非ゼロで終了します。help の表示成功とは区別し、共有ライブラリの探索やモデル読取りの実際の原因を隠しません。実装を追加するときは、help・前提不足・終了コードを CLI E2E で確かめます。

## 状態と拡張

可変状態、乱数、保存先、時刻などはインスタンスの協力相手として渡し、別のゲームやテストから独立させます。共有初期化やメインスレッドの制約を持つ処理は、その制約と並行利用の可否を明記します。DB・状態・乱数を分けることと、同じ状態の goroutine 安全性は別の契約です。

ゲーム側の拡張は利用側で定義する 1〜2 メソッドの小さな interface を優先します。複数の役割を一つの巨大な Host に束ねず、同じ役割には同じ名前と引数順を使います。差し替えの必要がない具体型を interface で包みません。画面に必要な値は下位の中立な値や小さな契約で受け渡し、下位から Ebitengine を参照しません。

## 変更の検査

`go test ./api` は OS・build tag に依存せず宣言済みの公開識別子の増減を見せます。更新は `go run ./internal/dev/apigen`。増加の理由は変更説明とレビューに残します。名前の一覧だけでは型・シグネチャ・意味の互換性を保証できないため、契約テストとレビューも必要です。詳しくは [API 検査](../development/api.md) を参照してください。
